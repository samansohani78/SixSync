# CLI reference

Generated by hand from the command definitions; `sixsync <command> --help` is
authoritative.

## Which commands change anything

| Command | Reads the gateway | Changes the gateway |
| --- | --- | --- |
| `version` | no | no |
| `lint` | no | no |
| `validate` | only with `--remote` | no |
| `doctor` | yes | no |
| `import` | yes | no |
| `drift` | yes | no |
| `plan` | yes | no |
| `apply` | yes | **yes**, with `--approve` |
| `rollback` | yes | **yes** |

`validate --remote` uses APISIX's schema endpoint, which validates its request
body and stores nothing.

## Global flags

| Flag | Environment | Meaning |
| --- | --- | --- |
| `--admin-url` | `SIXSYNC_ADMIN_URL`, `APISIX_ADMIN_API_URL` | Admin API base URL |
| `--admin-key` | `SIXSYNC_ADMIN_KEY`, `APISIX_ADMIN_API_KEY` | Admin API key |
| `--admin-key-file` | `SIXSYNC_ADMIN_KEY_FILE` | Read the key from a file (preferred) |
| `--ca-file` | `SIXSYNC_CA_FILE` | CA bundle for a private CA |
| `--client-cert-file` | `SIXSYNC_CLIENT_CERT_FILE` | Client certificate for mTLS |
| `--client-key-file` | `SIXSYNC_CLIENT_KEY_FILE` | Client key for mTLS |
| `--insecure-skip-tls-verify` | `SIXSYNC_INSECURE_SKIP_TLS_VERIFY` | Disable TLS verification. Warns on every run |
| `--timeout` | `SIXSYNC_TIMEOUT` | Per-request timeout, e.g. `10s` |
| `--output` | `SIXSYNC_OUTPUT` | `text` or `json` |
| `--repo-dir` | `SIXSYNC_REPO_DIR` | Directory holding resource files |
| `--config` | — | Path to a configuration file |

Precedence: flags, then environment, then the configuration file, then
defaults. `SIXSYNC_*` beats `APISIX_*`, so a SixSync-specific setting can
override one already in a pipeline.

The key is sent only as the `X-API-KEY` header. APISIX also accepts it as a
query parameter, which is avoided: query strings land in access logs.

## Commands

### `version`

```
sixsync version [--output text|json]
```

Takes its own `--output`, because it must work before any configuration exists.

### `doctor`

```
sixsync doctor
```

Reports reachability, TLS, authentication, key capability, the APISIX version,
and which resource kinds are managed. Never changes anything.

Capability is determined with a `DELETE` against an identifier APISIX cannot
store, so the request cannot destroy anything. See
[compatibility.md](compatibility.md) for why the obvious alternative does not
work on every version.

### `import`

```
sixsync import [--repo-dir DIR] [--dry-run] [--overwrite] [--kind KIND]...
```

Reads live resources into files, preserving APISIX identifiers exactly.
Existing files are never overwritten without `--overwrite`. Kinds carrying
credentials are refused by name with a reason.

### `lint`

```
sixsync lint [--repo-dir DIR] [--strict]
```

Checks the repository on its own — no endpoint, no credential — so it is safe
on a pull request from a fork. `--strict` treats warnings as failures.

Rules: `duplicate-id`, `invalid-id`, `dangling-reference`, `embedded-lua`,
`plaintext-secret`, `ephemeral-route`, `deletion-without-reason`.

### `validate`

```
sixsync validate [--repo-dir DIR] [--remote]
```

Structural checks always; with `--remote`, also APISIX's own schemas. Remote
validation needs a key that may use `POST` on APISIX 3.17.0 and later.

### `drift`

```
sixsync drift [--repo-dir DIR] [--detailed-exitcode]
```

Reports where the gateway and the repository disagree. A resource with no file
is reported as unmanaged, never as something to delete.

### `plan`

```
sixsync plan [--repo-dir DIR] [--out FILE] [--policy FILE]
             [--detailed-exitcode] [--approve-delete]
```

Writes a deterministic plan artifact. `--out` is required if you intend to
apply it: `apply` consumes an artifact and will not act on anything else.

### `apply`

```
sixsync apply --plan FILE [--repo-dir DIR] [--journal FILE]
              --approve [--approve-delete]
```

Executes a plan. Refuses without `--approve`; deletions additionally need
`--approve-delete`. Re-reads every affected resource before the first write and
abandons the run if anything moved.

### `rollback`

```
sixsync rollback --journal FILE [--out FILE] [--force]
```

Restores what an apply changed. Refuses if anything changed after the apply,
unless `--force`. Cannot restore credentials, because journals are redacted —
those are reported as manual steps.

## Exit codes

| Code | Meaning | Returned by |
| --- | --- | --- |
| 0 | Success, or no differences | all |
| 1 | Operational or validation failure | all |
| 2 | Differences found | `drift`, `plan`, with `--detailed-exitcode` |
| 3 | Remote state conflict | `apply`, `rollback` |
| 4 | Policy denied | `plan`, `apply` |
| 5 | Partial apply, or incomplete rollback | `apply`, `rollback` |
| 64 | Usage error | all |

Code 5 means live state is mixed and needs attention — deliberately distinct
from a plain failure, where nothing changed.

## A pipeline

```bash
# On every pull request. No endpoint, no credential.
sixsync lint --repo-dir .

# On the default branch, with a viewer key.
sixsync doctor
sixsync drift --repo-dir . --detailed-exitcode   # 2 means drift

# Before deploying, with a key that may write.
sixsync plan --repo-dir . --out plan.json --policy policies/production.yaml
# ... a human reviews plan.json ...
sixsync apply --plan plan.json --repo-dir . --journal journal.jsonl --approve

# If it goes wrong.
sixsync rollback --journal journal.jsonl
```
